**My own checks:**
- **[confirm]** Ran the test suite locally with `make test`, and all 50 tests passed.
- Played the whole demo quiz in the browser. Scoring, the speed bonus and the finish screen worked, with a final score of 577.
- **Found a bug in a two-player test.** I opened a second window and joined as "Mr B". It showed Mr A's finished quiz and score under the new name, with only one player on the leaderboard. The demo client kept the player ID in `localStorage`, which every window of the same browser shares, so both windows were the same player. The server behaved correctly: it treated this as a rejoin. The fix moved the ID to `sessionStorage`, which is per tab. A refresh still resumes the same player, but each new tab is a new player.
- **Why this matters:** none of the 50 automated tests could catch this bug, because they drive the server directly with a distinct `user_id` per player. It was only visible by using the real client the way a person would.

## Design phase

| Decision | How the AI arrived at it | How it was checked |
|---|---|---|
| Stateless nodes, with all live state in Redis | Derived from the scalability and reliability requirements, so any node can die without losing a quiz | `tests/test_multinode.py` runs two app instances on one shared fakeredis server. A score on node B appears on node A's leaderboard, and a player who reconnects to the other node resumes. |
| Server-authoritative scoring with a server-side timer | Derived from "accurate and consistent" scoring. Clients cannot be trusted with time or correctness. | Tests show that answering an unserved question is rejected, and that reconnecting does not reset the timer. |
| One atomic "dedupe, add points, bump version" operation, as a Lua script in Redis | Identified as the only way to rule out double-counting under retries and races | 50 concurrent identical submissions give exactly one accepted answer, on both stores |
| Coalesced leaderboard broadcast | Pushing on every answer costs O(N²) messages. Coalescing makes it O(N) per interval. | A unit test bounds the number of snapshots. The load test measured about 22,000 messages (22,010 and 21,706 in two runs) where the naive design would send 5,000,000. |
| "Latest wins" leaderboard slot and bounded queues | Stops one slow client from stalling the broadcast or growing memory without limit | `tests/test_hub.py` has a slow-client test and a stuck-client test |

## Issues found during verification

These are real problems the checks found in the AI's own first drafts, in the order they were found.

1. **A top-0 leaderboard read in Redis would have returned the entire sorted set.** In code review, the AI noticed that the hub's cheap "has anything changed?" check called `leaderboard(quiz, 0)`. In Redis that becomes `ZRANGE key 0 -1`, which returns everything. The fix added a dedicated `version()` method to both stores and a contract test for it.

2. **Slow-client protection did not work for a truly stuck socket.** The first design checked for overload inside the writer task. But if the writer is blocked inside a send to a dead socket, it never gets to that check. The fix is that the producer detects the overflow, cancels the writer, clears the queue and closes the socket out of band. `test_stuck_client_is_disconnected_and_memory_is_bounded` now pins this.

3. **The load test measured itself, not the server.** The first run reported a leaderboard latency of about 280 ms at the median, which was suspicious for a 100 ms window. The cause was that the simulated player slept for its think time inside its receive loop, so leaderboard pushes queued up unread. Moving the think time into a separate task brought the median to 88 ms, which matches the design.

4. **Mutation testing found a vacuous test.** `scripts/mutation_check.py` breaks one critical behaviour at a time. In its first run, removing the coalescing window still passed. The test's burst of 200 changes never yielded to the event loop, so everything coalesced trivially whether or not coalescing existed. The test now spreads changes over time and bounds snapshots by the number of 100 ms windows.

5. **Mutation testing found that failing tests hung instead of failing.** Three mutants hung the run rather than failing it, for two reasons:
   - Starlette's test WebSocket blocks forever on receive.
   - The join helper opened sockets without a guaranteed close, so a failed assertion blocked teardown.

   The fix added a receive with a 5-second timeout and turned `join()` into a context manager.

6. **A small efficiency fix.** Looking up a player's answered questions in the in-memory store scanned every answer in the quiz. It now uses a per-user index.

7. **Two browser windows were one player (found by the candidate, not the AI).** The AI-written client stored the player ID in `localStorage`, which is shared by every window of a browser. A "second player" was really the first player rejoining under a new name. The ID now lives in `sessionStorage`, which is per tab. The lesson: the AI's tests checked the server thoroughly, but nobody had used the client like a real person until the candidate did.

8. **The AI overstated its own verification in comments.** Early comments claimed the browser client and the app had been "exercised manually in a browser". That never happened, because the AI had no browser. The AI caught this when reviewing its own claims, and rewrote the comments to say exactly what was checked. Since then, every claim in the docs has been tied to a command that was actually run, and anything unrun is listed as unverified.

9. **The finish screen would have shown a blank rank.** While redesigning the page, the AI noticed that the server sends "quiz complete" before the leaderboard snapshot, so the rank on the finish screen was never filled in. The fix makes the leaderboard update keep the finish-screen rank current. This was found by reading the code and has not been checked in a browser.

## Known limits of the verification

- **No real Redis server.** Redis behaviour was tested with fakeredis, which runs the real Lua scripts through `lupa`. Differences from real Redis are possible, especially in pub/sub reconnection. The next step is running the contract suite against real Redis in CI with testcontainers.
- **Docker Compose and nginx not run.** No Docker was available.
- **Failure paths without automated tests:** graceful restart, a Redis outage, pub/sub resync, and publish failure. See TEST_RESULTS.md §6.
- **Browser client tested by hand only lightly.** The first version was played in one and two windows. The redesigned version should get the same two-tab check before the demo.
- **Load tests on one laptop.** The generator and the server shared 8 cores, so the absolute numbers are pessimistic for the server and should not be read as production capacity.
- **Failed connects at 4,000 players.** 31 connects failed in two of three runs at that scale. The cause was not confirmed. The leading hypotheses are the macOS listen backlog of 128 and ports left in TIME_WAIT by earlier runs.

## Takeaways on working with the AI

- The AI was fastest at breadth: protocol, stores, tests, metrics and documentation came together in one session.
- Its first drafts still had real bugs, in both code and tests. Green tests alone were not enough evidence. Mutation checks and load measurements found the problems that plain tests missed.
- Every performance or correctness claim in the docs is tied to a command that was actually run. Anything not run is listed above as unverified.
